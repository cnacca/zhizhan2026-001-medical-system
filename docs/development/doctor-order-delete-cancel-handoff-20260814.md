## 二、已经完成并验证的范围

### 1. 医生端草稿删除

- 草稿订单行提供“继续编辑 / 删除草稿”。
- 草稿筛选下支持选择后批量删除，单次最多 50 条。
- 删除采用软删除：保留订单主记录和审计事实，不物理删除历史订单。
- 草稿的 ACTIVE 附件同步标记为 `DELETED` 并写文件审计，不删除 MinIO 中的历史对象。
- 医生订单列表、患者历史和病例组读取过滤已删除草稿。
- 单条和批量请求均由服务端重新校验医生、诊所、草稿状态和病例组边界；批量任一项不合法时整批回滚。

对应 API：

```text
DELETE /orders/{orderId}/draft
POST   /orders/drafts/batch-delete
```

### 2. 医生端取消申请

- 仅 `PENDING_CS_REVIEW`、`PENDING_PRODUCTION_REVIEW` 两种内部状态允许医生提交取消申请。
- 入口位于订单行“更多”和订单详情抽屉。
- 必须填写取消原因。
- 重复提交返回已有的 `PENDING` 申请，保持幂等。
- 提交申请只新增审计事实，不删除订单，也不改变订单状态。
- 不提供批量取消。

对应 API：

```text
POST /orders/{orderId}/cancellation-requests
```

## 三、尚未实现，后续必须另开开发窗口

### P0-1 多产品病例草稿操作边界

当前后端拒绝从多产品病例中直接删除一个产品草稿，错误语义为“必须在病例编辑器管理”；但医生订单列表仍可能展示普通“删除草稿”入口。后续必须二选一并保持前后端一致：

1. 推荐：单产品草稿可直接删除；多产品草稿只显示“管理草稿”，在病例编辑器提供“删除整个病例草稿”。
2. 如果允许删除病例内单个产品，必须重新定义病例组完整性、共同患者资料、附件归属和剩余子订单行为，并增加原子事务测试。

批量删除也必须按病例组处理，不能让用户选中同一病例的部分子订单后才收到模糊 409。

### P0-2 客服端取消申请工作台

目前没有客服或管理员处理入口。后续至少需要：

- 待处理取消申请列表／筛选；
- 订单、患者、诊所、申请原因、申请人和申请时间展示；
- “同意取消”“拒绝取消”按钮；
- 审批备注；
- 权限码、诊所数据范围和管理员兜底边界。

建议新增服务端接口：

```text
GET  /order-cancellation-requests?status=PENDING
POST /order-cancellation-requests/{requestId}/approve
POST /order-cancellation-requests/{requestId}/reject
```

具体路径可在实现时按现有订单 API 风格校准，不能只做前端按钮。

### P0-3 真正的订单取消状态与状态机

当前状态机没有“已取消”，申请获批后也没有任何下游动作。实现前必须先补状态词汇和投影规则，至少明确：

- 新内部状态、新外部状态及其终态语义；
- 何时允许从待客服审核／待生产审核进入已取消；
- 审批时再次加锁检查当前状态，避免申请后订单已经投产仍被取消；
- 已取消订单禁止继续审核、设计、派工、生产、账单和发货；
- 医生端只能看到外部“已取消”，不得暴露内部审批或生产字段；
- 原订单、文件、审计和历史版本继续保留。

### P0-4 医生端结果反馈与通知

当前医生只能看到“取消申请处理中”。完整闭环还需要：

- 申请已通过／已拒绝状态；
- 拒绝原因；
- 是否允许重新申请；
- 是否允许在处理前撤回；
- 通知事件先落库，再通过通知中心／WebSocket 推送；
- 医生通知 payload 继续遵守内部信息脱敏红线。

### P0-5 审计、并发与回归

必须覆盖：

- 同意、拒绝、撤回（若启用）的操作者、原因和时间审计；
- 重复审批幂等；
- 两名处理人并发审批只成功一次；
- 申请后状态已变化时拒绝审批；
- 跨诊所、无权限和医生越权；
- 已投产、已发货、已完成订单不可走当前取消路径；
- 医生列表／详情／通知不返回内部字段；
- 多产品病例草稿单删、整组删和批删边界。

## 四、实现前必须确认的业务规则

以下不是“代码缺失就自动补”，而是产品规则待确认：

1. 哪些订单阶段允许申请取消；当前只临时限定在客服／生产待审核。
2. 由谁处理；建议由客服统一受理，生产待审核订单由客服向生产确认后处理，管理员保留兜底权限。
3. 审批通过后，报价、账单、已付款、退款、设计任务、生产任务、物流和文件分别如何处理。
4. 是否允许医生撤回待处理申请。
5. 拒绝后是否允许重新申请，以及是否要求新的原因。
6. 是否允许管理员恢复已取消订单；若允许，必须另建恢复审计和状态门禁，不能直接改库。

在这些规则确认前，不实现自动退款、自动删除设计／生产事实或自动恢复订单。

## 五、建议的最小完整方案

后续若没有更具体的产品口径，建议按以下最小闭环提案向业务确认：

1. 医生只能在客服审核中、生产审核中申请取消。
2. 客服统一同意／拒绝；生产审核中的订单由客服先线下确认未投产。
3. 同意后进入外部终态“已取消”，保留全部历史事实，禁止进入后续流程。
4. 一期不自动退款；已付款订单只生成“退款待人工处理”待办。
5. 拒绝后允许重新申请一次；处理前允许医生撤回。
6. 不提供批量取消；批量操作只用于草稿软删除。

该方案目前是建议，不是已确认事实。

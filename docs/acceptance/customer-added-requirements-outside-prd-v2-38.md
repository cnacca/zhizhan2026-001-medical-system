# 客户新增需求（PRD V2 原 38 项之外）

状态：ACTIVE / 2026-08-04

## 为什么单列这份

`docs/acceptance/prd-v2-38-item-acceptance-audit-20260715.md` 的 38 项是 PRD V2.0 的验收基线，
条目数本身被多处引用（「30 PASS / 1 PARTIAL / 7 EXTERNAL_ACCEPTANCE」等口径）。

客户在 2026-07-24 的确认清单里提出了 PRD 原文没有的新需求。这类需求**做了，但不能混进 38 项计数**——
一旦混进去，「38 项完成多少」这个口径就和历史记录对不上，而且分不清哪些是原范围、哪些是后加的。
因此单独记在这里。

## 条目

### CA-001 账号交接与人员转移

- **来源**：客户原话「有分配功能，把他账号分配给新同事，并保留之前得服务记录」。
- **PRD V2 原 38 项中无对应条目**（TASK-034 D 小节已注明）。
- **落地**：TASK-034 D 批次，迁移 `V83__account_handover.sql`，
  接口 `POST /accounts/{userId}/handover` 等 4 个，
  校验入口 `npm run check:task-034-account-handover`。
- **状态**：`DONE`（2026-08-04）。
- **验收证据**：
  - 后端 `AccountHandoverTests`（11 项）与 `AccountHandoverClassificationTests`（3 项）；
  - 演示环境真实登录实测：医生 9701 的 17 条订单、5 条患者档案、9 个病例组、21 个资料
    转给承接医生 9799，而 14 条状态流转、1 条沟通消息、22 条文件访问留痕、8 条病例组审计
    全部仍归原责任人。
- **边界**：客户口径的「转移负责的客户」目前只能落到订单上的 `cs_user_id`。
  客户↔负责人的一级关系（clinic 级）在系统里尚不存在，依赖 GOAL-034 G4；
  该关系落地后需要加入 `AccountHandoverPlan.TRANSFER_RULES`，
  届时 `AccountHandoverClassificationTests` 会强制做出分类判断。

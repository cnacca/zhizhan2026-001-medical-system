# 客服端配送管理页面重构确认稿

> 状态：业务方案已确认；前端功能重构、HTML像素校准及真实浏览器验收已完成；后端能力仍有缺口
> 确认日期：2026-07-18
> 权威视觉参考：`frontend/public/reference/cs-portal.html`、`frontend/public/reference/doctor-portal.html`

## 1. 设计结论

配送管理定位为待发货订单、发货登记、物流进度和配送异常工作台。账单与配送继续保留两个独立菜单；配送页不再展示账单队列或收款操作。

确认采用以下方案：

1. 保留参考页的承运商选择卡、承运商官网跳转、物流进度卡、最新事件和物流时间线；
2. 一期继续采用人工登记发货、人工维护物流进度和人工异常跟进；
3. 承运商官网跳转只是操作便利入口，不代表已接入 DHL、FedEx、UPS、EMS 或其他物流 API；
4. 发货前必须同时通过终检、客户付款/结算政策和收件资料门禁；
5. 发货成功后通知医生/诊所，医生端可以查看物流并确认收货；
6. 物流异常需要独立留痕，需联系客户时进入问单沟通；
7. 管理员只读，配送业务由客服经理或获得配送权限的高级客服处理。

## 2. 参考文件映射

客服端参考页 `page-billing` 下半部分提供 Shipment Tracking：

- “Book New Shipment”入口；
- DHL、FedEx、UPS、EMS 承运商卡片；
- 跳转承运商官网预约取件；
- 订单、发货日期、服务类型、重量、地址、申报价值、保险和运单号；
- 配送卡片、物流阶段线、最新事件、官网追踪和时间线详情。

当前项目已确认账单和配送拆成两个页面，因此上述配送部分全部移入本页，账单表格、应收金额和收款操作留在账单管理。

参考原型中的物流事件是静态演示数据，官网追踪是外部链接，没有真实物流 API 集成。正式页面不能把静态轨迹或官网跳转表述成系统自动同步。

## 4. 发货门禁

```text
最后一道工序终检出检通过
            +
客户付款/结算政策允许发货
            +
收件人和收件地址完整
            ↓
         允许登记发货
```

### 4.1 终检门禁

- 必须存在该订单最后一道工序的 `OUT/PASS` 记录；
- 终检未完成、未通过或订单处于返工状态时禁止发货；
- 配送页只读取终检结果，不允许客服修改生产质检数据。

### 4.2 付款与结算门禁

- 按单付款客户：该订单满足已确认的付款放行条件后才能发货；
- 月结客户：按照客户商务条款放行；达到逾期暂停条件时禁止发货；
- 页面直接显示放行结果和原因，不要求配送人员自行推断账单状态；
- 付款规则不满足时显示“暂缓发货 / 等待收款”或对应业务原因。

### 4.3 收件资料门禁

- 收件人、联系电话、国家/地区和完整地址必须存在；
- 地址来源于客户管理，但发货时保存配送快照；
- 地址缺失时进入客户管理补充，不允许使用演示地址；
- 当前不提供普通管理员强制跳过门禁的按钮。

## 6. 配送卡片

### 6.1 待发货卡片

待发货卡片显示：

- 订单号、诊所、产品和计划发货日期；
- 终检门禁、付款门禁和地址门禁；
- 可以发货时显示“登记发货”；
- 暂缓发货时明确展示阻塞原因和正确处理入口。

### 6.2 已发货卡片

已发货卡片显示：

- 订单号、承运商和运单号；
- 当前运输进度和异常状态；
- 最新物流事件、发生时间和地点；
- 运单创建、已揽收、运输中、已清关、派送中和已签收阶段线；
- 官网追踪和查看详情按钮；
- 当前数据来源：“人工更新”或未来的“承运商同步”。

在没有真实物流 API 时，阶段线只能根据客服人工记录和医生确认收货更新，不能使用静态演示事件冒充真实轨迹。

## 8. 状态口径

发货状态、运输进度和异常处理必须分开：

| 状态类型 | 页面状态 | 含义 |
| --- | --- | --- |
| 发货状态 | 待发货、暂缓发货、已发货、已签收 | 订单配送主状态 |
| 运输进度 | 运单已创建、已揽收、运输中、已清关、派送中、已送达 | 包裹运输阶段 |
| 异常处理 | 正常、配送异常、跟进中、已解决 | 客服异常处理进度 |

三个状态可以同时表达，例如“已发货 + 运输中 + 配送异常/跟进中”。“已解决”表示异常处理完成，不等于包裹已经签收。

## 9. 物流异常跟进

客服记录异常时至少填写：

- 异常类型：延误、清关、地址问题、拒收、丢失、破损或其他；
- 异常发生时间；
- 当前处理状态；
- 内部跟进说明；
- 是否需要通知客户；
- 下一次跟进时间；
- 负责人。

异常处理流程：

```text
发现配送异常
      ↓
记录异常事实和负责人
      ↓
需要客户确认 ──→ 问单沟通
      ↓
记录每次跟进结果
      ↓
问题解决后标记“已解决”
      ↓
包裹继续运输或进入后续处理
```

配送管理只保存异常事实和处理记录。对外消息在问单沟通中由客服人工编辑并发送。

## 10. 医生端联动

- 登记发货后向对应诊所/医生发送订单已发货通知；
- 医生端展示承运商、运单号、发货时间、公开运输进度和官网追踪入口；
- 客服内部异常说明、责任人和审计记录不得返回医生端；
- 医生确认收货后，订单状态和配送签收时间同步更新；
- 医生确认收货不是物流平台自动签收回调，两者需要在页面上区分来源。

## 11. 权限边界

| 角色 | 页面与数据范围 | 权限 |
| --- | --- | --- |
| 客服经理 | 全部客户配送订单 | 查看、登记发货、更新进度、处理异常 |
| 获得配送权限的高级客服 | 分配给自己的客户 | 按授权处理配送订单 |
| 普通客服 | 默认不可见 | 只在订单或问单中查看必要配送摘要 |
| 翻译人员 | 不可见 | 无配送权限 |
| 管理员 | 只读配送总览 | 查看配送和异常记录，不登记发货或更新进度 |
| 医生/诊所 | 医生端只读 | 查看本诊所物流并确认收货 |
| 生产人员 | 不可见 | 负责终检结果，不录入物流 |

菜单隐藏不能代替后端权限和客户数据范围校验。配送列表、详情、地址、发货、进度、异常和导出接口必须使用一致的数据范围。

## 12. 页面联动

| 配送操作 | 去向/结果 |
| --- | --- |
| 查看订单 | 进入对应订单详情 |
| 等待收款 | 进入账单管理的对应账单 |
| 补充收件资料 | 进入客户管理的诊所地址资料 |
| 发起客户沟通 | 进入对应订单或客户的问单沟通 |
| 生产终检未通过 | 只显示生产门禁原因，不允许客服修改生产数据 |
| 医生确认收货 | 回写订单完成状态和配送签收时间 |

## 13. 当前系统已实现能力

当前项目已有以下基础能力，后续重构应复用：

1. 客服人工录入承运商和运单号；
2. 发货前最后一道工序必须存在 `OUT/PASS` 终检出检记录；
3. 发货后订单状态更新并通知医生；
4. 配送列表和物流状态筛选；
5. 人工记录配送异常、跟进中和已解决状态；
6. 异常跟进说明作为客服内部消息留痕，不向医生端公开；
7. 医生端查看物流并确认收货。

## 14. 当前系统缺口与后续实施项

以下缺口已记录，但不在当前方案讨论阶段实施：

1. 当前 `order_logistics` 只完整使用承运商、运单号、简化状态和发货时间，缺少服务类型、重量、收件快照、申报价值、保险和预计送达时间；
2. 当前只有一个混合 `logistics_status`，没有拆分发货状态、运输进度和异常处理状态；
3. 当前没有独立物流事件表，时间线无法保存多条结构化事件；
4. 当前没有真实物流 API、电子面单、自动轨迹同步、签收回调或物流平台 webhook；
5. 当前配送列表未完整计算终检、付款/结算政策和收件资料三项门禁；服务端发货只强制校验终检 `OUT/PASS`；
6. 当前客户档案缺少完整收件地址、账单/配送联系人和地址快照能力；
7. 当前异常跟进复用客服内部消息，不是独立异常与跟进记录模型；
8. 当前医生确认收货只更新订单状态，没有同步写入 `order_logistics.delivered_at`；
9. 当前没有承运商目录、官网地址配置、受信域名校验和跳转审计；
10. 当前只有顶层 `CS` 角色，没有配送专项权限、客服岗位层级和客户分配数据范围；
11. 当前 CS 和 ADMIN 都可以写入物流及异常，与目标“授权客服处理、管理员只读”不一致；
12. 当前页面为简化列表和异常表单，没有参考页的承运商卡片、配送卡片、阶段线、结构化详情和时间线。

## 15. 实施边界

- 配送管理业务方案已经冻结，当前只执行前端 HTML 像素校准；未接入的物流后端能力继续明确展示为空态或能力边界；
- 不接真实物流 API，不伪造实时轨迹；
- 承运商官网只作为受信外部链接，不自动传输客户或患者数据；
- 发货门禁必须在后端执行，不能只在前端禁用按钮；
- 实施后需覆盖终检门禁、付款门禁、地址门禁、发货通知、异常跟进、医生端脱敏、确认收货和权限数据范围；
- 后续若接入真实物流平台，需要另行确认供应商、API、费用、回调验签、状态映射和隐私边界。

## 1. 实施结论

完整业务闭环仍不能只靠菜单和页面样式完成。当前系统把客服统一建模为顶层 `CS`，默认数据范围为 `ALL`；确认稿则要求区分客服经理、高级客服、普通客服和翻译人员，并让订单、问单、客户、账单、配送、外协、搜索和附件使用同一数据范围。本轮先完成已授权的前端结构、真实接口适配、空态与像素验收，并把后端缺口保持为明确边界。

因此采用以下实施顺序：

```text
B0 现状基线与模块边界
        ↓
B1 岗位、权限、客户分配与统一数据范围
        ↓
B2 客服端壳层、菜单、顶栏与工作台接入
        ↓
B3 订单管理与“新订单 → 已登记”
        ↓
B4 问单沟通基础能力与双栏会话
        ↓
B5 信息审核/翻译与问单回写
        ↓
B6 设计稿管理与设计确认问单
        ↓
B7 客户管理 → 产品管理 → 设置与账号
        ↓
B8 账单管理与自动月结
        ↓
B9 配送管理 → 外协管理
        ↓
B10 通知 → 帮助 → 全局搜索
        ↓
B11 全页面像素、权限、主链与回归验收
```

推荐按上述顺序实施。B3—B6 是一期客服主链，优先级高于 B7—B10；B11 只在全部页面接入真实数据后执行。

## 2. 已核对的当前实现事实

### 2.1 前端

- 客服端、医生端、生产端和管理端主要集中在 `frontend/src/App.vue`，当前约 1.7 万行；
- 客服端视觉样式集中在 `frontend/src/cs-portal.css`，但页面逻辑仍与其他端混合；
- 当前客服菜单仍包含“待审核订单”“沟通中心”“智能助手”和侧栏“通知中心”，与确认稿不一致；
- 账单和配送共用 `/delivery`，设计稿复用订单页，外协复用生产成本页；
- 当前订单页仍使用“客服初审”“待客服初审”；
- 顶栏已有搜索、日期、通知和“＋ 新建订单”占位，但缺少帮助入口、真实搜索弹层和统一状态恢复；
- 当前工作台已有真实指标和确认保留的“信息评审/翻译待审”，主体不重做。

### 2.2 权限和身份

- 顶层角色只有 `DOCTOR / CS / WORKER / ADMIN`；
- `DatabaseAuthService` 和 `AccessControlService` 当前对 `CS`、`ADMIN` 默认返回 `ALL`；
- 数据库已经有 `system_post`、`system_user_post`、权限和菜单表，可以承载客服岗位，不需要先增加四个新的顶层 `UserRole`；
- 当前身份只返回角色、权限和单一数据范围，不返回岗位代码；
- 当前多个服务各自拼接 `clinic_id / cs_user_id` 条件，尚未形成客服端统一业务范围服务；
- 当前管理员通过角色兜底可以进入多项客服业务写入接口，与“系统管理员只管理系统、业务能力另行授权”的确认口径冲突。

### 2.3 业务基础

- 订单已有 `cs_user_id`，但没有客户级负责人、协作客服和分配历史；
- 订单已有 `/orders/{id}/review`，语义是客服审核，不是已确认的“登记订单”；
- 消息、关注事项、设计稿、按单账单、收款记录、物流、通知和外协只读查询已有部分基础；
- 尚无统一问单事项、信息审核/翻译任务、月结账单、客户级分配、常用回复、通知偏好和统一搜索模型；
- 产品接口当前允许 `CS / ADMIN` 新增和编辑，与“不做新增产品、管理员业务只读”的确认方案冲突；
- 外协当前只有列表和详情，`supplier_name` 是自由文本，没有地点、合作方、批准来源和客服跟进接口。

## 3. 总体技术拆分

### 3.1 前端拆分目标

实施时新建客服端独立模块，建议结构如下：

```text
frontend/src/portals/cs/
├── CsPortalShell.vue
├── navigation.ts
├── permissions.ts
├── api/
├── components/
│   ├── CsPageHeader.vue
│   ├── CsFilterBar.vue
│   ├── CsStatusBadge.vue
│   ├── CsRightDrawer.vue
│   ├── CsEmptyState.vue
│   └── CsPermissionState.vue
├── pages/
│   ├── CsWorkbenchPage.vue
│   ├── CsOrderManagementPage.vue
│   ├── CsInquiryCommunicationPage.vue
│   ├── CsTranslationReviewPage.vue
│   ├── CsDesignDraftPage.vue
│   ├── CsCustomerManagementPage.vue
│   ├── CsProductManagementPage.vue
│   ├── CsBillingManagementPage.vue
│   ├── CsDeliveryManagementPage.vue
│   ├── CsOutsourcingManagementPage.vue
│   ├── CsSettingsPage.vue
│   ├── CsNotificationPage.vue
│   ├── CsHelpPage.vue
│   └── CsSearchPage.vue
└── styles/
    ├── tokens.css
    ├── shell.css
    └── pages/
```

约束：

- 不为本轮额外引入路由或状态管理依赖；先通过适配层复用当前 `activeRoute / activeNavId` 机制；
- `App.vue` 只保留客服端挂载、身份和跨端公共能力，页面业务逐批迁出；
- `cs-portal.css` 在迁移期作为兼容层，页面迁完后再删除失效规则，不能一次性重写影响其他端；
- 菜单、按钮、字段和 Badge 全部由真实权限和接口响应决定，不使用静态演示数组；
- 每迁移一个页面就停止渲染该页面在 `App.vue` 中的旧分支，避免双实现并存；
- 参考 HTML 只用于视觉和交互，不复制演示数据、姓名、金额、时间和 `localStorage` 状态。

### 3.2 后端拆分目标

建议保留顶层 `UserRole.CS` 作为端口身份，通过岗位、权限和业务范围实现细分：

```text
顶层角色 CS
  ├── 岗位：CS_MANAGER     客服经理
  ├── 岗位：CS_SENIOR      高级客服
  ├── 岗位：CS_AGENT       普通客服
  └── 岗位：TRANSLATOR     翻译人员

岗位 + 专项权限 + 客户/订单/任务分配
                  ↓
统一业务数据范围服务
                  ↓
列表 / 统计 / 详情 / 搜索 / 导出 / 附件 / 写入使用同一判定
```

推荐新增统一的客服业务访问策略服务，不允许每个页面各写一套 SQL 条件。至少统一处理：

- 全部客户及团队业务；
- 分配客户；
- 本人负责订单和问单；
- 分配翻译任务及其关联订单；
- 账单、配送、外协等专项权限；
- 系统管理员的业务授权，而不是 `ADMIN` 角色自动放行。

数据库迁移使用当前 V44 之后的下一个可用版本号，实际开始实施时再次检查分支上的最新迁移，不能提前固定并占用版本号。

### 3.3 订单状态拆分原则

“登记”不替代生产状态，也不复用现有“客服审核”：

```text
订单主状态：生产与对外进度，继续由现有状态机管理
登记状态：新订单 / 已登记
信息状态：待处理 / 处理中 / 等待客户回复 / 待二次确认 / 已完成
设计状态：按设计稿版本管理
```

登记记录、翻译版本、问单和设计版本均保存独立事实与审计，不无痕覆盖 `orders.form_data` 中的客户原始内容。

## 4. 分批实施计划

### B0：现状基线与客服模块边界

**目标**：建立可比较、可回退的重构起点，不改变现有业务行为。

**实施内容**：

1. 固化客服端当前路由、接口、角色和页面截图基线；
2. 建立新客服模块目录、挂载适配层和视觉 token；
3. 为其他端关键入口增加最小回归保护，防止拆 `App.vue` 时误伤；
4. 建立页面迁移清单，标明旧分支、目标组件和删除时点；
5. 固化参考页 SHA-256 和 `1440×900` 截图规则。

**非目标**：不改菜单、不改状态词、不改接口、不改数据库。

**完成门禁**：新模块可以空挂载；医生端、生产端、管理端和当前客服端行为无变化；前端构建通过。

### B1：岗位、权限、客户分配与统一数据范围

**依赖**：B0。

**目标**：先解决所有页面共同依赖的权限和范围问题。

**实施内容**：

1. 在 `system_post / system_user_post` 中增加并分配四类客服岗位；
2. 身份响应增加岗位代码和可用客服能力，不把岗位硬编码在前端；
3. 新增客户负责人、协作客服、有效期、变更原因和历史记录；
4. 继续保留订单负责人，但明确客户分配和订单分配的继承、覆盖关系；
5. 新增客服业务范围服务，统一返回可访问客户、订单、问单和任务范围；
6. 拆分页面读取、页面写入和专项业务权限，例如翻译、设计、账单、配送、外协、团队设置；
7. 移除敏感业务接口仅凭 `ADMIN` 或 `CS` 角色兜底放行的做法；
8. 菜单响应只返回有权进入的页面，但后端接口仍单独鉴权；
9. 为四种客服岗位和系统管理员建立权限矩阵测试。

**重点验收**：

- 客服经理可以访问全部客户和团队业务；
- 高级客服只访问分配客户及获授权专项页面；
- 普通客服只访问本人订单和问单；
- 翻译人员只访问分配任务、必要附件和关联问单；
- 系统管理员不因 `ADMIN` 自动读取或写入客户业务；
- 列表、数量、详情、导出、搜索、附件和写入不存在范围差异。

**风险**：这是影响范围最大的底座批次。必须通过后端集成测试和其他端回归后，才能进入 B2。

### B2：客服端壳层、菜单、顶栏与工作台接入

**依赖**：B1 的身份和菜单能力。

**目标**：按统一确认稿完成端内框架，工作台主体保持不变。

**实施内容**：

1. 实现固定 `236px` 侧栏、`56px` 顶栏和统一页面标题区；
2. 左侧菜单改为 11 个业务入口，并按岗位与权限显示；
3. 删除侧栏通知、帮助和智能助手独立菜单；
4. 顶栏按“当前页面 / 搜索 / 数据时间 / 通知 / 帮助 / ＋ 新建订单”排列；
5. “＋ 新建订单”只实现已确认的按钮入口和名称，不显示数量，不在本批次新增客服代下单流程或 `POST /orders`；
6. 账号区按岗位进入团队设置或个人设置；不实现登录、切换端口和参考演示账号；
7. 将现有工作台放入新壳层，保留主体、指标和“信息评审/翻译待审”；
8. 菜单切换保留页面筛选、选中项、滚动位置和辅助页返回状态。

**像素验收**：`1440×900` 下核对侧栏宽度、顶栏高度、间距、颜色、纹理、字体层级、Hover、Active、Badge、空态和无权限状态。

### B3：订单管理与登记流程

**依赖**：B1、B2。

**目标**：把“客服初审”改为真实的“新订单 → 登记订单 → 已登记”。

**后端与数据**：

1. 增加独立登记状态、登记人、登记时间、登记备注和登记审计；
2. 提供幂等 `登记订单` 接口，重复请求不重复创建任务或日志；
3. 登记成功后可靠创建信息审核/翻译任务；
4. 列表响应拆分登记状态、信息状态和订单主阶段；
5. 支持确认稿中的筛选、默认排序、分页、统计和导出；
6. 停止让客服使用 `/orders/{id}/review` 完成登记；现有生产审核语义保留在生产审核链路；
7. 原始下单信息保持只读，客服登记不能修改客户原文。

**前端**：

1. 实现订单列表、快捷筛选、新订单行级高亮和 `540px` 右侧详情抽屉；
2. 登记按钮、状态反馈、并发冲突和重复提交处理；
3. 详情提供信息审核/翻译、问单、设计、账单、配送和外协的授权跳转；
4. 抽屉顶部保留订单摘要，正文按“制作时间线 → 订单资料 → 文件与设计 → 沟通信息 → 订单记录”连续排列并由整个抽屉滚动；制作时间线使用全部真实工序，沟通区与“问单沟通”共用同一订单消息数据，不提供绕过翻译或生产审核的发布按钮。

**验收主链**：医生提交订单 → 新订单置顶 → 客服登记一次 → 状态显示已登记 → 生成且仅生成一个翻译任务。

### B4：问单沟通基础能力与双栏会话

**依赖**：B1、B2；B3 提供真实订单和负责人关系。

**目标**：将现有消息能力整理为“会话 + 问单事项 + 自由交流”，为翻译和设计确认提供统一出口。

**后端与数据**：

1. 在现有 `order_message` 基础上增加统一问单事项实体；
2. 保存问单类型、来源页面、关联业务对象、负责人、状态、优先级、关闭结果和审计；
3. 完成消息未读、真实发送时间、会话负责人、超时提醒和附件关联；
4. 明确对客消息、生产草稿和内部备注三类可见性；
5. 只有客服可向客户发送；翻译和生产只能提交疑点或草稿；
6. 继续复用医生端允许的消息投影，严禁暴露内部工序、员工、工时、返工、责任和生产备注。

**前端**：

1. 实现左侧会话列表、筛选、搜索和未读/超时状态；
2. 右侧实现真实消息时间线、自由输入、附件、可编辑快捷回复和事项卡；
3. 快捷回复只填入输入框，不自动发送；
4. 支持转派、处理、关闭和定位来源记录；
5. 不建立独立“设计确认”页面。

**验收主链**：创建问单 → 客服自由发送 → 医生端只见对客内容 → 客户回复 → 关联事项收到结果 → 关闭后保留历史。

### B5：信息审核/翻译

**依赖**：B3 的任务创建、B4 的问单关联。

**目标**：把散落在客服初审中的翻译、资料检查和生产备注移交翻译岗位。

**后端与数据**：

1. 建立信息审核/翻译任务、负责人、状态、开始/完成时间和等待时长；
2. 分开保存客户原文、AI 草稿、人工确认稿、结构化生产信息和生产备注版本；
3. 增加任务分配、领取、保存草稿、确认版本、创建问单和完成接口；
4. 未解决疑点阻止任务完成；客户回复后进入“待二次确认”；
5. 信息完成后进入生产审核，不由客服越级发布；
6. AI 内容必须人工确认，保留提示、模型和操作审计；
7. 附件、AI 调用和导出使用翻译任务范围。

**前端**：实现任务队列、信息审核、翻译整理、附件、处理记录、版本差异、保存冲突和问单回写状态。

**验收主链**：登记订单 → 分配翻译 → 保存人工确认稿 → 有疑点时创建问单 → 客户回复 → 二次确认 → 完成 → 生产只读取最终确认版本。

### B6：设计稿管理与设计确认问单

**依赖**：B4；读取 B5 订单级确认信息。

**目标**：完成设计文件版本、版本执行信息、内部审核和客户确认回写。

**实施内容**：

1. 在现有设计稿版本基础上增加当前版本执行信息、修改来源、原因和审计；
2. 保留客户原始指示、订单级确认信息和设计版本调整值，不互相覆盖；
3. 实现订单列表、状态排序和 `540px` 详情面板；
4. 支持多文件版本、私有预览、审核通过、驳回和版本过期冲突；
5. “发起设计确认”在 B4 中创建带版本预览的设计确认问单；
6. 医生确认、驳回或留言后回写当前版本状态；
7. 客服不能代替客户确认，生产人员不能看到不必要的客户私密内容。

**验收主链**：生产上传版本 → 授权客服审核 → 发起确认问单 → 医生查看授权版本并确认/驳回 → 设计列表和问单同步结果。

### B7：客户、产品、设置与账号

**依赖**：B1；B4 提供问单跳转。

#### B7.1 客户管理

1. 扩展诊所国家、地址、邮箱、收件/账单联系人、销售/客服负责人等业务档案；
2. 增加商务条款、结算政策、价格等级、信用信息、合同摘要和风险规则；
3. 增加医生/成员业务资料和账号开通申请，不在客服端创建登录凭据；
4. 实现客户列表、风险卡、详情和四步新建业务档案；
5. 高级客服只见分配客户，普通客服和翻译无客户总表；
6. 客户偏好只作为新订单默认参考，不反向修改历史订单。

#### B7.2 产品管理

1. 删除客服端“新增产品”入口，不实现新产品申请或审批；
2. 将读取和维护已有产品拆成不同权限，管理员业务只读；
3. 产品与医生下单要求建立稳定关联和变更记录；
4. 医生下单从已启用产品目录选择，订单保存产品快照；
5. 页面只使用“医生下单要求”等业务语言，不展示“动态字段/字段类型”等技术词；
6. 不实现模板草稿、发布版本或新增产品。

#### B7.3 设置与账号

1. 客服经理查看团队成员和客户分配，但不能创建、停用、解锁账号或改密码；
2. 普通岗位只显示个人常用回复和通知偏好；
3. 建立团队/个人常用回复、版本和停用记录；
4. 建立个人通知订阅和显示偏好；
5. 客户分配变更保存原负责人、新负责人、操作人、时间和原因；
6. 登录账号管理继续留在管理端，客服端只显示业务状态和账号开通申请结果。

**B7 门禁**：客户月结配置完成后，才允许进入 B8 的自动月结实施。

### B8：账单管理与自动月结

**依赖**：B7 的客户结算配置和产品/订单金额依据；B4 提供收款提醒问单。

**实施前必须确认的业务门禁**：

1. 订单在生产完成、终检通过、发货还是按单账单上传后计入月结；
2. 加急费、返工折扣、补差价和其他调整的入账方式；
3. 作废、跨期调整和已部分收款订单的处理；
4. 多币种是否拆分月结单；
5. 节假日或系统停机后的补生成规则。

上述五项未确认时，可以完成数据结构和非计算性页面准备，但不能上线自动归集任务或声称自动月结已完成。

**实施内容**：

1. 保留现有按单账单，补齐编号、到期日、发送状态和逾期依据；
2. 新增月结主表、订单明细快照、生成批次、异常和调整审计；
3. 收款记录可关联按单账单或月结账单，并从有效记录计算已收/未收；
4. 自动生成任务具备并发锁、幂等键、失败回滚、补偿和防重复占用；
5. 自动生成只创建草稿，不自动收款、不自动发送、不反算历史价格；
6. 实现按单/月结页签、筛选、详情、核对、调整、确认、发送、作废和收款记录；
7. 收款提醒跳转问单，由客服编辑并确认发送；
8. 账单文件、金额、导出和写入使用账单专项权限。

**验收主链**：到达生成日 → 生成唯一草稿和快照 → 客服核对并发送 → 人工登记部分/全部收款 → 正确计算未收与逾期；重复执行不重复生成。

### B9：配送管理与外协管理

**依赖**：B1、B3；配送依赖 B8 的付款/结算结果，外协依赖生产批准来源。

#### B9.1 配送管理

1. 拆分发货状态、运输进度和异常处理状态；
2. 补充服务类型、重量、收件快照、申报价值、保险和预计送达；
3. 增加结构化物流事件和异常跟进记录；
4. 后端统一校验终检、付款/结算政策和收件资料三项门禁；
5. 实现待发货/已发货卡片、登记发货、详情、阶段线和异常跟进；
6. 医生确认收货同时更新订单完成状态和 `delivered_at`；
7. 第一期不接物流 API、电子面单或实时轨迹，不伪造物流数据。

#### B9.2 外协管理

1. 建立外发地点和合作方档案，以稳定 ID 关联批次；
2. 增加合作方启停、联系人、地址、擅长范围和默认周期；
3. 增加外协批准来源、负责人、客户范围、履约状态和风险状态；
4. 增加登记、更新、返回、取消、进度事件和异常跟进接口；
5. 外协件返回只通知生产检查，不直接改生产工序完成状态；
6. 客服经理和授权高级客服登记/跟进，管理员只读；
7. 正式数据必须使用客户提供或后台配置的地点/合作方，不使用演示地点；
8. 不做合作方账号、外部聊天、文件自动外传、成本结算或地图。

### B10：通知、帮助与全局搜索

**依赖**：B1 和全部目标业务页面的稳定路由、状态与权限。

#### B10.1 通知中心

5. 点击后重新鉴权并定位具体记录；
6. 投递规则使用岗位和客户范围，不向普通客服投递无权业务。

#### B10.2 帮助中心

#### B10.3 全局搜索

## 8. 主要风险与控制

| 风险 | 影响 | 控制方式 |
| --- | --- | --- |
| 只改菜单、不改数据范围 | 严重越权 | B1 必须先完成，接口逐项做角色矩阵测试 |
| 直接重写 `App.vue` | 误伤四端 | 按页面迁出，保留适配层，每批回归其他端 |

| CSS 全量替换 | 像素回退或跨端污染 | token + 页面样式逐批迁移，旧样式最后清理 |
| 辅助页先做 | 搜索和通知无稳定目标 | 通知、帮助、搜索排在业务页面之后 |

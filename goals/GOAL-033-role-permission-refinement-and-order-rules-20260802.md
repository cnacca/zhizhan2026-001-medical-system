## 调研结论（本 Goal 的立论依据）

### 结论一：RBAC 表结构已完整，缺的是数据与管理界面

现有 11 张 RBAC 表：`system_user` / `system_role` / `system_menu` / `system_post` / `system_dept` / `system_permission` 及 `system_user_role` / `system_role_menu` / `system_user_post` / `system_role_permission` / `system_user_permission`。

`system_dept` **已支持层级**（`parent_id`），现有数据已是三层：

```
100 牙科定制工厂
 ├─ 110 客服中心
 ├─ 120 生产中心
 │   ├─ 121 CAD 设计组
 │   ├─ 122 切削加工组
 │   └─ 123 上瓷质检组
 └─ 130 管理中心
```

**客户欠的"真实部门/班组清单"只是替换这批演示数据，不阻塞机制建设。**

### 结论二：细分角色不需要扩 `UserRole` 枚举

`UserRole`（`DOCTOR`/`CS`/`WORKER`/`ADMIN`）在 **48 个文件中被引用 553 处**。若把客户的 20 个细分角色做成枚举值，需改动全部引用，风险极高。

但客户已确认两条规则，使这一步可以避免：

1. 「医生端、客服端、生产端、管理端**必须使用各自入口登录**，账号角色与入口不匹配时拒绝登录」— ☑同意
2. 「一个账号允许有多个角色，但**登录后必须选择『当前身份』**；切换身份后重新加载权限，**不能把多个角色权限自动相加**」— ☑同意

第 2 条意味着**任一时刻只有一个生效身份**，与现有 `BootstrapIdentity.role()` 单值模型天然兼容。

因此确定架构口径：

> **`UserRole` 保持 4 个值，语义收敛为「入口角色 / Portal」。**
> 客户的 20 个细分角色一律表达为 `system_role` 记录 + 权限码集合 + 数据范围，不进入枚举。

映射关系：

| 入口角色 | 承载的细分角色 |
| --- | --- |
| `DOCTOR` | 诊所管理员、医生、前台、护士/助手 |
| `CS` | 客服经理、普通客服、翻译人员、**收货人员**、**发货人员** |
| `WORKER` | 生产经理、部门/班组主管、**组长**、技工、质检员、终检员 |
| `ADMIN` | 管理员、经理、主管、普通员工 |

已有 **48 个权限码**与 **198 个 `@RequirePermission` 注解**，权限码层已成型，是承载细分角色的现成载体。

### 结论三：`data_scope` 挂错了位置

`data_scope` 目前是 `system_user` 的列（每用户一个值）。客户的模型按**角色**定义数据范围：客服经理=全公司、高级客服=分配客户、普通客服=本人负责。

因此需把 `data_scope` 提升到 `system_role`，用户级保留为覆盖项。这是本 Goal 中唯一的数据模型变更。

### 结论四：授权层是混合模式，需统一

`AccessControlService` 现存三种判定并行：

- `requireAnyRole(...)` — 纯角色白名单，**不看权限码**
- `requirePermissionOrRole(...)` — 权限码或角色
- 硬编码组合，如 `requireProductionReview` 写死 `ADMIN || (WORKER && hasPermission)`

纯角色白名单的调用点会让新细分角色失效——新角色仍是 `WORKER`，但拿不到只对特定角色开放的入口。需逐个改为权限码判定。

### 结论五：下单规则前端已做、后端零实现

`try_in_required`、过程确认、订单类型、运输类型在 `DoctorCaseGroupWizard.vue` 中已有字段，后端检索命中 0。后端**完全没有交期计算逻辑**（`due_date` / `deliveryDate` / `expectedDelivery` 在后端 Java 中零命中）。

当前表现：医生能勾选，但不计价、不排期、不延长工期。**比未实现更危险——演示时看起来功能齐全。**

## Acceptance

- 新增一个细分角色（如「组长」）只需在管理端配置，**不需要改任何 Java 代码**。
- `data_scope` 可按角色配置，用户级可覆盖；订单、工序、绩效、文件的数据过滤按之生效。
- `AccessControlService` 中不再存在纯角色白名单判定，全部走权限码。
- 管理端可创建/停用/编辑角色、分配菜单与权限码、维护部门与岗位层级、给用户分配角色——**可实操，非只读**。
- 账号停用时可将其负责的客户/订单/任务转移给指定同事，历史记录保留原责任人不变。
- 导出行为按客户规则受控：医生端不可导出；客户信息/地址/账单导出需审批；其余导出留痕。
- 下单时选择试戴、过程确认、加急后，后端据此产生可验证的后果（计价项、交期变化、状态分支）。
- 全部新增守卫有对应的越权拒绝测试。
- Task 8 保持 `NOT_READY`。

## Risks

- 客户三项澄清未回前，「高级客服」「管理端代操作生产」「生产资料审核员」三处的最终形态不确定。B 批次需把这三项做成配置可调，而非写死。
- 2026-07-30 刚按 PRD 完成的生产审核授权，客户已勾「取消生产资料审核员」。改动前必须先取得澄清，否则可能返工两次。
- 交期计算依赖客户未提供的各产品标准制作周期。F 批次只建规则引擎与默认值占位，真实数值待 CP 项到位。

### 执行中偏离原计划的三处

1. **结论三有两处事实错误**（A 批次已纠正）：`data_scope` 本来就在 `system_role` 上，不需要"提升"；
   真正让角色级配置失效的是 `resolveDataScope` 里的入口角色短路。
2. **结论五低估了工作量**：F 批次不只是"补后端实现"，还要先统一任务书 / 客户确认表 / 前端三处
   互相冲突的字段叫法，并把「哪些订单类型要回寄运单号」的自相矛盾之处按验收口径定下来。
3. **E 批次开工时发现客户第一条要求正被违反**：医生端有两个纯前端拼 CSV 的按钮，
   无审批无留痕地带走患者姓名与金额。因此 E 不是"给现有导出加审批"，而是先把数据出口收回后端。

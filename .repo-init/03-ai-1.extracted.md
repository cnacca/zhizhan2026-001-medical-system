1. 大白话概括：我们到底要做个什么东西

一句话：给一家牙科定制工厂做一套『在线下单 + 生产管理 + 客户查询』的网站系统，让医生在网上下单做牙，工厂内部把活分下去、一道道工序做、做完发货，客户能随时查进度——而且客户只能看到『做到哪步了』，看不到工厂内部谁在做、花了多久、出过什么问题。

系统分三个『端』（三类人用三个不同的界面）

还要加一个 AI 助手

AI 在这一期只做『打下手』，不做决策：帮客服翻译、帮客户/客服查『这单做到哪了、啥时候发货、物流到哪了』、提醒医生『资料没传齐』、把客户要求整理成规范的生产备注。关键的审核、医疗判断、设计确认还是人来定。

3. 三个角色的职责、报酬与工作量

3.1 项目经理（1500 元）—— 总指挥 + 架构 + 对客户

定位：他是这个项目里『拍板的人』，对最终交付负总责。不只是排进度，更要把需求定死、把架构定好、把客户对齐。

具体职责：

整体把关：对交付质量、进度、验收负总责，是三人中的最终决策者。

定技术栈：评估并决定后端用什么语言/框架、用哪些开源底座（参考第 6 节），选『最合适、最能复用、最快落地』的那套，并对全栈交底。

制定精确需求：把本文档的需求细化成可执行的页面清单、字段清单、状态流图、工艺模板清单、权限清单、API 契约；消除一切模糊地带。

架构设计：定数据库模型、模块边界、内外状态映射表、权限与脱敏方案——这些是后面所有开发的地基。

与客户对齐：需求确认、阶段演示对接、验收口径确认；客户有变更先经他评估再决定要不要做。

代码把关：review 全栈提交的关键 PR（尤其架构/权限/脱敏相关），是合并到主干的最终批准人。

工作量：贯穿全程。重活集中在前期（定需求/定架构约需 3–4 天集中产出）和每个里程碑的收口验收对接（每个里程碑约 1 天）。

3.2 全栈开发 / 落地工程师（2000 元）—— 把系统真正写出来 + 演示

定位：他是『真正把代码写出来』的人，报酬最高因为活最重。三人里他承担主要开发产出，并负责给客户做演示。

具体职责：

按项目经理定的架构和需求，落地三端的前后端功能：下单、审核、文件、工艺流、入检出检、工时绩效、AI 接入、账单物流、消息通知等。

最大化复用开源底座（第 6 节），不重复造轮子；把省下的精力投到工艺流引擎、状态脱敏、AI 权限过滤这些必须自研的业务核心。

写出可测试、可演示的功能，配合验收工程师走查、修复其提的缺陷。

负责演示：每个里程碑/阶段向项目经理和客户演示已完成的功能，能讲清楚做了什么、怎么用。

遵守 Git 协作规范（第 7 节），所有代码经 PR、经项目经理 review 后合并。

工作量：全程满负荷，是三人中投入最大的角色。每个里程碑都是他的主战场。

3.3 验收测试工程师（1000 元）—— 走完整流程，把关质量

定位：他是『用户的眼睛』，负责把每一条业务流程从头到尾走一遍，找出 bug 和不符合需求的地方，确保交付的东西真的能用。

具体职责：

走完整流程：按技术方案第 12.1 节的 12 步主链路，从医生下单一路走到客户查到已发货，逐步验证每个环节对不对。

写测试用例：覆盖正常流程 + 异常流程（驳回、补资料、返工、权限越界、脱敏泄露、AI 越权）。

重点测脱敏和权限：专门验证『医生端看不到内部信息』『客户端 AI 不泄露内部细节』——这是合规红线，必须死磕。

提缺陷给全栈修复，复测确认；对每个里程碑出具『是否通过』的验收结论。

遵守 Git 协作规范，缺陷以 Issue 形式记录、可追溯。

工作量：前期写用例（约 1–2 天），中后期随每个里程碑集中测试（每个里程碑约 1–2 天），是阶段尾部的主力。

7. 三人协作与 Git / PR 规范

仓库已建好（zhizhan2026-001-medical-system，私有）。三人协作的核心原则：谁都不许直接往主干推代码，所有改动走分支 + PR + review。

7.1 分支怎么开

7.2 标准协作流程（每个人每天这样干）

从 dev 切出自己的 feature/fix 分支：git checkout dev && git pull && git checkout -b feature/order-create。

在分支上写代码，小步提交：git commit -m "feat: 完成订单创建表单"（提交信息写清楚做了什么）。

推到远程：git push origin feature/order-create。

在 GitHub 上发起 PR（Pull Request），目标合并到 dev，并 @项目经理 review。

项目经理 review：看代码质量、是否符合需求/架构、权限和脱敏有没有漏。有问题打回改，过了才批准合并。

合并进 dev 后，验收测试工程师在 dev 上走流程测试，发现问题提 Issue，全栈开 fix 分支修。

一个里程碑功能稳定、测试通过后，由项目经理把 dev 合并到 main，打个版本标签（如 v0.4-M4）。

7.3 提交信息规范（让历史可读）

7.4 协作铁律

严禁直接 push main：GitHub 仓库设置里给 main 开『分支保护』，强制 PR + review 才能合。

严禁提交密钥：.env（数据库密码、AI 的 API key）必须写进 .gitignore，绝不能传上去——这是医疗系统，泄密后果严重。

每个 PR 尽量小、聚焦一个功能，方便 review；别攒一大坨一次性提。

测试提的每个 bug 都开一个 Issue，关联对应 PR，做到可追溯。

每天同步一次进度（哪怕一句话）：谁在做什么、卡在哪、需要谁配合。

本文档怎么用
本期按技术方案完整一期交付：三端 + 可配置工艺流 + 入检出检 + 工时绩效 + 5 个 AI 智能体 + 内外脱敏。
推进方式：按里程碑完成度推进——做完一个里程碑、验收通过、回款到位，再进入下一个。
提效思路：通用模块尽量复用成熟开源底座（见第 6 节），把精力集中在业务核心上，又快又稳。

谁在用 | 通俗说就是 | 他们能干嘛
医生端 / 客户 | 下单的人（牙医诊所） | 网上填单子、传 STL 模型/照片/X光、确认设计稿、查进度、看账单物流。只能看简化进度。
客服端 / 中台 | 中间对接的人 | 审核医生的单子、把外文需求翻译成中文生产指令、催医生补资料、对接账单物流、用 AI 帮忙查单。
生产端 / 工厂 | 工厂里干活的人 | 审数据、派活、按工艺流程一道道做、每道工序做前检查(入检)做后检查(出检)、记工时、出绩效、质检、发货。

最核心的一条业务主线（记住这条就懂了整个系统）
客户下单 → 客服审核 → 工厂审数据 → 生成工艺流程 → 设计做稿 → 医生确认 → 一道道工序生产(入检·做·记工时·出检) → 质检 → 发货 → 客户查到『已发货』。
只要这条主线能从头跑到尾、且客户看不到工厂内部细节，系统就算立起来了。

复用的铁律
① 所有开源项目用前，由项目经理逐个确认 license 可商用（MIT/Apache 一般可，注意 Dify 这类有多租户/LOGO 附加条款的要绕开）。
② 开源省下的时间，全部投到三块自研硬骨头：可配置工艺流引擎、入检出检工时绩效、内外状态脱敏。这三块也是最容易烂尾、最需要 PM 把关的地方。

分支 | 用途 | 谁动
main（主干） | 随时可上线的稳定代码，受保护，禁止直接 push | 只有 PM 能批准合并
dev（开发主线） | 日常集成分支，功能合到这里联调 | 全栈合 PR 进来
feature/xxx（功能分支） | 每个功能/模块单独开一条，如 feature/order-create | 全栈，从 dev 切出
fix/xxx（修复分支） | 修 bug 用，如 fix/login-token | 全栈，对应测试提的 Issue

前缀 | 含义 | 例子
feat: | 新功能 | feat: 完成入检出检记录
fix: | 修 bug | fix: 修复医生端泄露工时字段
refactor: | 重构不改功能 | refactor: 抽出状态映射工具
docs: | 文档 | docs: 补充 API 说明
test: | 测试相关 | test: 增加脱敏越权用例

权限与人数提醒
仓库是私有的，记得把全栈、测试拉进仓库协作者（Settings → Collaborators），并给 main 开分支保护、把『合并 PR 需要 review 批准』打开。
